# Bug Audit Report — renquant_104 (2026-04-24)

Comprehensive code-level audit of every Task, Job, Pipeline, adapter, and
support module under `backtesting/renquant_104/`. Findings are catalogued
below by module, with severity tags:

- 🔴 **CRITICAL** — silent correctness bug; results & live trades affected.
- 🟠 **HIGH** — wrong behaviour in a known scenario; bug surfaces under realistic config.
- 🟡 **MEDIUM** — edge-case / consistency / dead-code issue.
- ⚪ **LOW** — style, doc, or nit-pick (still worth fixing).

The bugs the user already filed (Bug 11, 12, 16, 25, 26, 28, 29) are not
re-listed; this audit catalogues what is *still in the tree* today.

────────────────────────────────────────────────────────────────────────
## 1. Pipeline framework — `kernel/pipeline/pipeline.py`

### 1. 🟠 `should_skip()` is dead code on `Job` and `TickerJob`
- `Job.should_skip` and `TickerJob` (no `should_skip`) — but the base
  `Job.run()` never consults it. Only `pp_training.TrainingPipeline.run`
  and `pp_training_full.FullTrainingPipeline.run` call `should_skip`.
- Effect: `RankingJob.should_skip`, `SelectionJob.should_skip`,
  `RotationJob.should_skip`, `PanelScoringJob.should_skip` are all
  defined but **never honored** — their guard logic is silently bypassed.
- `pp_inference.InferencePipeline.run()` calls `RankingJob().run(ctx)`
  directly, ignoring `should_skip`.

### 2. 🟡 `run_parallel` cancel-on-timeout is a no-op
- `fut.cancel()` after `TimeoutError` — but `concurrent.futures` cannot
  cancel a future that has *started* running (and threads-only executor
  cannot interrupt running thread). The "TIMEOUT — skipped" log is
  misleading: the worker keeps consuming CPU until it returns naturally.

### 3. 🟡 `run_parallel` reads `parallel_workers` only from `ticker_ctxs[0]`
- If different tickers carry different configs (they shouldn't, but
  there is no enforcement), the first ticker's config silently wins.

## 2. Inference pipeline orchestrator — `pp_inference.py`

### 4. 🔴 Defensive bear-only universe builder skips OHLCV check
- `_buy_universe` (line 88-90):
  ```python
  defensives = set(ctx.config.get("defensive_tickers", []))
  return [t for t in defensives if t in ctx.models and t not in held]
  ```
  Compare to the non-bear branch which also requires `t in ctx.ohlcv`.
  Effect: in BEAR / `bear_only`, a defensive ticker (GLD / TLT / etc.)
  whose OHLCV failed to load will still produce a `TickerInferenceContext`
  whose `BuildFeaturesTask` will return `False` — but only after wasted
  thread spin-up. Worse: any task before `BuildFeaturesTask` in the chain
  (e.g. `EarningsFilterTask`) that doesn't gate on missing OHLCV could
  generate a candidate from empty data and crash downstream.

### 5. 🟠 Counter `blocked_streak` is incremented from wrong attribute
- Line 116-117:
  ```python
  elif tc.exit_signal is not None and getattr(tc.exit_signal, "_blocked_streak", False):
      ctx.counters["blocked_streak"] += 1
  ```
  This works, but `tc.exit_signal` here is the same dataclass instance
  written by `EvaluateExitsTask` — which sets `_blocked_streak = True`
  via `sig._blocked_streak = True` on a frozen-by-convention `ExitSignal`
  dataclass that is *not* `frozen=True` so the attribute write succeeds.
  The mismatch between docstring "should_exit=False" and `tc.exit_signal
  not None` semantics makes the next reader believe an exit fired.

### 6. 🟡 SellOnlyPipeline does not run `BuyGatesJob`
- That is intentional, but it also doesn't run `MonitorIdleStreakTask` or
  `BuyGatesJob.DrawdownGateTask`. After an intraday exit window, the
  monitor streak is not advanced, so on the next full bar the no-trade
  alert is undercounted.

### 7. 🟡 Pipeline output ordering reversed for top-up vs trim
- Comment says "TopUp skips over-target, Trim skips under" — true. But
  both tasks read `ctx.exits` to decide what's already exiting, and both
  use the **broken** `getattr(e, "ticker", None)` pattern (see #20-#22)
  so neither guard works. End result: a stop-loss exit on a ticker
  doesn't stop top-up or trim from also emitting an order on it.

## 3. Regime layer — `task_regime.py`, `kernel/regime.py`

### 8. 🟡 `HurstTask` short-circuits with `None`, not `False`
- `if len(spy_returns) < 30: return None` — chain continues to CUSUM/GMM/
  BEAR-override even with insufficient data, where they fall back to
  defaults. Inconsistent semantics; should probably return `False` to
  let `RegimeFinalizeTask` use whatever previous-bar state is on
  `regime_state` instead of mixing fresh fallbacks with stale state.

### 9. 🔴 `compute_hurst` lag/value misalignment in polyfit
- `kernel/regime.py:101`:
  ```python
  lags_used = list(range(2, 2 + len(rs_vals)))
  poly = np.polyfit(np.log(lags_used), np.log(rs_vals), 1)
  ```
  `rs_vals` is appended only when `rs_chunk` is non-empty for that lag.
  If lag=3 produced no chunks (n too small for stats with ddof=1), then
  `rs_vals[1]` corresponds to lag=4, but `lags_used[1]=3`. The Hurst
  exponent is the regression slope on log-log, so a misaligned lag axis
  silently biases the result.

### 10. 🟡 `compute_hurst` chunk loop off-by-one
- `chunks = [arr[i:i+lag] for i in range(0, n - lag, lag)]` — last chunk
  starts at `n - 2*lag` (when `n` is a multiple of `lag` plus `lag`).
  The trailing `arr[n-lag:n]` chunk is silently skipped. Should be
  `range(0, n - lag + 1, lag)`.

### 11. 🟡 BEAR override uses `np.sum(returns)` as cumulative return
- `task_regime.BEAROverrideTask` line 109: `spy_20d_ret = np.sum(returns[-20:])`
  treats arithmetic returns as additive. Acceptable approximation for
  small returns but documented as "spy_20d_cumret" — the strict math is
  `prod(1 + r) - 1`. With a 25 % drop, sum = 0.25 vs prod = 0.22; the
  threshold-based BEAR latch fires slightly differently than docs imply.

### 12. 🟡 `cooldown_start` snapshot mismatch sim vs live
- `RegimeFinalizeTask` records `cooldown_start = datetime.datetime(y,m,d)`
  for sim (date-only `today`), but `datetime.datetime.utcnow()` for the
  fallback. In live where `today` is `datetime.date`, the path taken is
  the date-aligned one, *not* utcnow. Result: live + sim cooldowns are
  computed with midnight-aligned starts, which tracks fine intraday but
  overstates "elapsed" by up to 24 h on a freshly-armed cooldown.

### 13. 🟡 `cusum_cooldown_progress` returns 1.0 (no penalty) when `now is None`
- The fallback is "no penalty"; but the only reasonable cause for `now`
  being None is a programming bug in the caller. Failing closed (return
  0.0 → no buys) would be safer; the current behaviour silently pretends
  the cooldown has elapsed.

### 14. 🟡 `RegimeFinalizeTask` clears `cooldown_start` based on bar countdown only
- Comment promises wall-clock cleanup but the guard is
  `if state.countdown == 0 and state.cooldown_start is not None: …
   if cusum_cooldown_progress(now, cooldown_start, cd_days) >= 1.0:`
  Inside the if, only clears `cooldown_start`. If `cd_days` is *bigger*
  than `transition_uncertainty_bars`, the wall-clock progress can be < 1.0
  and `cooldown_start` lingers forever — affecting size scaling but never
  re-arming the bar counter. Docs claim "fully elapses" but the bar-count
  side has already elapsed by the time we reach this branch.

## 4. BuyGates — `task_gates.py`, `job_gates.py`

### 15. 🟠 BEAR / Confidence veto / BullVol veto stop the rest of the gate chain
- `BEARBranchTask`, `ConfidenceVetoTask`, `BullVolOffensiveBlockTask` all
  return `False`, halting the chain. That means in BEAR (or
  confidence-veto) regimes, neither `VelocityCrashTask` nor
  `EMA50GateTask` ever fires. **Effect**: `buy_blocked` stays False
  while `bear_only=True`. Defensive purchases in `_buy_universe` still
  proceed even during a SPY velocity crash or sub-EMA50 macro downtrend.

### 16. 🟡 `EMA50GateTask` tolerates None-spy_df silently
- `if spy_df is not None and check_spy_ema_trend(...)`: if `spy_df` is
  missing, gate is skipped (no `buy_blocked=True`, no warning). A SPY
  data outage silently disables the macro filter.

## 5. Sell pipeline — `task_sell.py`, `kernel/exits.py`

### 17. 🟡 `EvaluateExitsTask` writes `_blocked_streak` to `ExitSignal`
- `sig._blocked_streak = True   # noqa: SLF001` on a dataclass that
  doesn't declare the attribute. Works because dataclasses aren't frozen,
  but adds a non-typed attribute. Should be a real field on `ExitSignal`.

### 18. 🟡 Tax-hold gate uses hardcoded 365-day threshold
- `compute_exits` line 251: `if lt_gate <= days_held < 365:` ignores the
  config'd `long_term_threshold_days`. If a user changes that to 366
  (or any non-365 jurisdiction), the tax gate fires on the wrong window.

### 19. 🟡 `compute_exits` updates `state.high_watermark` before any check
- Line 208: `state.high_watermark = max(hwm, current_price)`. This means
  the trailing stop's `peak_gain` is computed *after* HWM is bumped to
  the same bar's price, so a brand-new high never triggers trailing
  stop on the same bar. Documented in the docstring of
  `check_trailing_stop` as a "by design" edge case, but the consequence
  is a one-bar lag for trailing exits on momentum tops.

## 6. Top-up / Trim — `task_topup.py`, `task_trim.py`

### 20. 🔴 `task_topup.py` already_selling guard is broken (tuple .ticker)
- Line 59:
  ```python
  already_selling = {getattr(e, "ticker", None) for e in getattr(ctx, "exits", [])}
  ```
  But `ctx.exits` is `list[(ticker, ExitSignal)]`. `getattr(tuple, "ticker", None)`
  returns `None`. **Result**: `already_selling = {None}`, the membership
  check below is always false, and TopUpHeldTask happily emits a BUY
  for a ticker the SellJob already exited. The adapter then has to
  resolve a same-bar buy after a same-bar sell — which `RunnerAdapter`
  rejects via the duplicate-order guard, but `LeanAdapter` does not.

### 21. 🔴 `task_trim.py` already_exiting guard is broken (same bug)
- Line 73 — identical bug. Worse than #20 because `TrimHeldTask` *adds*
  an `ExitSignal` of its own to `ctx.exits`. If a real stop-loss exit
  on the same ticker is already there, the trim's signal is appended
  too — `SimAdapter._apply_sell` is called twice for the same ticker
  in `commit()`. The second call reads `_pos_shares[ticker]` which by
  then is whatever the first call left (full liquidation leaves it
  unchanged because the pop happens after the loop). Result: the
  position can be sold *twice* with phantom cash credited.
- Compounding: `last_sell_dates[ticker]` is set by both calls, blocking
  the next bar's wash-sale for the longer window.

### 22. 🔴 `live/runner._notify_decision` shows `EXIT ? (?)` for every exit
- Line 309-312:
  ```python
  for e in exits:
      tkr    = getattr(e, "ticker", "?")
      reason = getattr(e, "exit_type", getattr(e, "reason", "sell"))
      parts.append(f"EXIT {tkr} ({reason})")
  ```
  Same tuple-attr-getattr bug. ntfy notifications log every exit as
  `EXIT ? (?)`. Operationally this means the user can't tell which
  position was just sold via an alert.

### 23. 🟠 Top-up overstates `target_pct`
- `task_topup.py:108-115`:
  ```python
  bought_delta = min(delta, per_session_cap)
  …
  target_pct = (current_pct + delta)   # uses original delta, not bought_delta
  ```
  When `per_session_buy_cap` clips the delta, the order's `target_pct`
  is the *uncapped* target. Audit logs and DB rows now claim the order
  filled to the wrong target.

### 24. 🟠 Top-up does NOT update HWM, but SimAdapter does
- `_apply_buy` for an existing ticker (top-up path) does
  `high_watermark = max(prev_hwm, today's buy price)`. Top-up at a
  *higher* price ratchets the HWM up, tightening the trailing stop
  immediately. Top-up at a *lower* price has no effect on HWM (max),
  so the trail doesn't loosen. Asymmetric behaviour — not catastrophic
  but it makes top-up subtly more dangerous than implied.

### 25. 🟠 Trim's `target_floor` guard hides over-weight stale Kelly
- `if kelly_target < target_floor: continue` — the guard description
  says "let regular exit path handle conviction loss." But if a position
  is over-weight *because Kelly target dropped recently*, this guard
  prevents the trim. The user pays for the conviction loss with a wider
  drawdown until a model-sell exit eventually fires (3 consecutive sell
  signals + min_hold_days). Tradeoff is documented in the comment but
  the alternative behaviour is not exposed as a config knob.

## 7. Selection — `task_selection.py`, `kernel/selection.py`

### 26. 🟠 `RotationJob` runs **before** `SelectionJob` but rotation orders
   bypass per-session-cap, Kelly-target sizing, and CUSUM cooldown.
- `EmitRotationsTask` computes `max_pct = base_max_pct * conv * sig_m`
  and ignores: (a) `kelly_cfg.disable_extra_multipliers`, (b)
  `kelly_target_pct` from the candidate, (c) `per_session_buy_cap`,
  (d) the `cooldown_mult` scaling that `SizeAndEmitTask` applies during
  CUSUM wall-time cooldown. So rotation buys are *full-sized* during
  cooldown while fresh-pick buys are scaled down. This breaks the
  "Kelly is one number in one place" invariant promised in `kernel/kelly.py`.

### 27. 🟠 `SizeAndEmitTask` order field omits `kelly_target_pct` when not Kelly
- The order dict carries `kelly_target_pct` only via
  `getattr(c, "kelly_target_pct", None) if c else None`. Live/sim
  adapters then stamp `entry_kelly_target_pct = order.get("kelly_target_pct")`.
  When Kelly is disabled, `c.kelly_target_pct` is None on every
  candidate (set by `ApplyKellySizingTask` only when enabled). Result:
  every freshly-bought position has `entry_kelly_target_pct = None`,
  breaking thesis-A rotation gating's fallback rule "no baseline → keep
  pair." Effect is benign in the OFF-flag case but fragile.

### 28. 🟡 Selection's correlation guard fails on exact-zero correlation
- `kernel/selection.py:97-99`:
  ```python
  corr = (corr_matrix.get(ticker, {}).get(held)
          or corr_matrix.get(held, {}).get(ticker))
  ```
  `0.0 or X` short-circuits to X; should be an explicit `None`-check.
  Edge case but matters when correlation snapshots round to 0.

### 29. 🟡 BEAR-mode sector guard bypass for defensives
- `passes_sector_guard` returns True for any ticker in `defensive_set`.
  In BEAR, multiple defensives in the same effective sector (e.g.
  XLU + XLP + XLV) can pile up regardless of `max_positions_per_sector`.
  Plan O fixed the non-BEAR loophole; the BEAR side is still wide open.

### 30. 🟡 `SizeAndEmitTask` oversize fallback hardcodes 25 %
- `compute_position_size` falls back to `0.25 * portfolio_value` when
  the confidence-scaled max can't cover one share. The fallback ignores
  the regime, ignores BEAR override, and ignores cooldown — so it can
  emit a BUY at 25 % during a CUSUM cooldown that was supposed to scale
  size to ~0.

### 31. 🟡 `RankingJob.should_skip` references `ctx.bear_only` *before*
   `BuyGatesJob` has run if `BuyGatesJob` returned False on its first task.
- Not currently triggered (BuyGatesJob is always sequential in `pp_inference`),
  but it relies on the chain ordering invariant. Nothing actually invokes
  `should_skip` (see #1), so the bug is latent.

## 8. Rotation — `task_rotation.py`, `kernel/rotation.py`

### 32. 🟠 `_drive_score` returns mismatched units when scoring_mode is
    "mu_minus_lambda_sigma" but only one side has μ/σ
- `BuildPairsTask:_drive_score` falls back to `expected_return` when μ/σ
  are missing. Consequence: `cand_er = μ−λσ` (small magnitude, e.g. ±0.05)
  while `held_er = expected_return` (calibrated probability-derived,
  range 0..0.10). Computing `raw_adv = cand_er - held_er` mixes scales;
  rotation may fire spuriously or refuse to fire depending on ordering.

### 33. 🟠 `EmitRotationsTask` re-uses `base_max_pct` ignoring Kelly path
- Same as #26. `EmitRotationsTask` does not branch on
  `kelly_sizing.enabled`; it always uses `base_max_pct * conv * sig_m`.
  When Kelly is enabled in `SizeAndEmit`, the two surfaces silently
  disagree on what "target weight" means.

### 34. 🟡 `find_thesis_primary_pairs` allows entry_score≤0 to skip silently
- `if entry_score is None or entry_score <= 0: continue` — but a held's
  baseline at zero might be a legitimate "neutral" entry. Skipping it
  means low-quality holdings whose entry_score happened to be ≤0 cannot
  be rotated out via thesis_primary mode.

### 35. 🟡 `find_rotation_pairs` `held_max_unrealized_pct` semantics
- Documented as "protect hot runners" — but `if unreal_pct > held_max_unreal: continue`
  also locks in **losers below max_unreal** (e.g. 5 % gain). Combined
  with the LT-protection gate, eligible holdings shrink quickly.

### 36. 🟡 `find_rotation_pairs` persistence gate fails closed too early
- "When fewer than N bars of history have accumulated, we require all
  history to contain the pair (fail-closed)." The code:
  ```python
  required = min(persistence, len(prior_proposals))
  if required < persistence: continue
  ```
  Combined with the line above, it actually fails closed — but the
  description is misleading. On a fresh start with empty history,
  `required = 0` and the `< persistence` check returns True → continue
  (no rotation). Fine; but if `persistence_bars` is 1 and history is
  empty, `required=0 < 1` → skip — even though the gate could be
  trivially satisfied by today's proposal alone.

### 37. 🟡 `ValidatePairsTask` virtual-held set construction operator precedence
- `set - set1 - set2 | set3` evaluates as `(((set - set1) - set2) | set3)`.
  Intended. But difficult to read; one missing parenthesis would silently
  re-order operations and break the guard. Worth wrapping explicitly.

### 38. 🟡 `BuildPairsTask` in `thesis_symmetric` mode returns silently when DB
   is missing
- `db is None → 0 pairs` with a single warning. The user's contract is
  "live + sim should always have DB"; LEAN runs without it intentionally.
  But there's no fallback — V4 is a complete no-op in LEAN. A user
  enabling thesis_symmetric expecting LEAN behaviour will see *zero*
  rotations and not know why.

## 9. Panel scoring — `kernel/panel_pipeline/job_panel_scoring.py`

### 39. 🟠 `BuildFeatureMatrixTask` returns False if `feature_frames is None`
   short-circuits the whole chain
- This kills `LoadGlobalCalibrationTask`, `LoadNGBoostTask`, etc. Even
  if the caller has pre-computed an NGBoost head, it never runs because
  the Task chain stops at BuildFeatureMatrix.

### 40. 🟠 `ApplyNGBoostTask` updates `panel_score` on holdings but NOT `rank_score`
- For candidates: `cand.rank_score = cand.panel_score = combined`. Symmetric.
- For holdings: only `hs.panel_score = combined`. `hs.rank_score` stays
  whatever `ApplyScoresTask` (or `ScoreModelTask`) left there. So
  rotation comparisons (uses `rank_score`) and exits (uses `rank_score`)
  see *different* values for held vs candidate when ngboost is in
  `mu_minus_lambda_sigma` mode. Calibration step fixes this for held
  too — but only when global calibration is enabled. With ngboost on
  but global calibration off, the asymmetry persists.

### 41. 🟡 `ApplyGlobalCalibrationTask` no `regime` field on holdings
- The per-regime calibrator dispatch uses `ctx.regime`. Holdings stored
  on `ctx.holdings` have no per-position regime; they are scored under
  *today's* regime even if they were entered in a different one. That's
  by design (calibrator is regime of *today's market*), but it's a
  surprise to a reader.

### 42. 🟡 `LoadScorerTask`'s `artifact_path` is resolved against `_strategy_dir`,
   but `LoadGlobalCalibrationTask` has its own resolver
- Two different `_resolve` lambdas across tasks; if one is updated to
  fallback differently (e.g. accept absolute paths), the other still
  silently uses the old behaviour. Refactor to a shared util.

### 43. 🟡 `VetoWeakBuysTask` does not surface counter when no candidates dropped
- `if dropped: ctx.counters["panel_vetoed"] += dropped`. When dropped=0
  the counter doesn't exist. Downstream observers reading this counter
  see KeyError or fall back to 0.

### 44. 🟡 `PanelScoringJob.should_skip` is dead code (see #1)

## 10. Training pipelines — `pp_training.py`, `pp_training_full.py`

### 45. 🟠 `_run_ticker_chain` `tc.exported = True` on TTL-skip even though `tc.result is None`
- Downstream callers reading `ctx.exported` see this ticker as "exported
  this run", but the artifact on disk could be stale. Combined with
  `panel_oos_ic` retraining metadata that reads `ctx.exported`,
  TTL-skipped tickers can be mis-attributed.

### 46. 🟠 `DataFetchJob` hardcodes "SPY" benchmark
- Line 309: `set(ctx.watchlist) | set(sector_etf.values()) | {"SPY"}`.
  But config supports `benchmark` field. If user changes benchmark to
  e.g. QQQ, training fetches SPY anyway and the panel never sees QQQ data.
  `pp_training_full.FetchPanelDataTask` *does* read config.benchmark —
  inconsistent.

### 47. 🟡 `RegimeCombineTask` gathers `regime_probs.loc[dt].get(r, 0.5)` for
   regime CHOPPY — but CHOPPY isn't a GMM cluster label
- The fallback 0.5 is then never used because the CHOPPY branch above
  computes Hurst-based confidence first. Dead branch but confusing.

### 48. 🟡 `_apply_column_migrations` only handles `training_runs`
- Other tables (e.g. `pipeline_runs`, `candidate_scores`) have evolved
  too. Fresh installs are fine; existing DBs would silently miss new
  columns until manually migrated.

### 49. 🟡 `FilterStalenessTask.run` uses `date.today()` not a context "today"
- For sim, the fresh/stale check is pegged to wall-clock today. A
  backtest from 2020 with models trained 2026 will see all models as
  "fresh". A backtest from 2020 with models trained 2018 sees all as
  "stale". Either case introduces lookahead or starvation depending on
  artifact dates. Should accept an explicit `as_of_date` kwarg.

### 50. 🟡 `TickerCalibrationJob` swallows all exceptions
- `try: …  except Exception as exc: print(f"  {tc.ticker}: TickerCalibrationJob failed — {exc}")`.
  Combined with `if not tc.exported or not tc.result or tc.feature_frame is None: return`,
  any unexpected error in calibration is invisible in production logs
  beyond a `print`.

## 11. Adapters — `adapters/{lean,runner,sim}.py`

### 51. 🔴 `LeanAdapter.commit` ignores `ExitSignal.quantity` (partial sell)
- The exit loop calls `algo.Liquidate(sym)` for every `(ticker, sig)`
  in `ctx.exits`, regardless of `sig.quantity`. LEAN's `Liquidate`
  always closes the entire position. So a Kelly trim with `quantity=10`
  on a 100-share position dumps all 100 shares. Partial-sell
  infrastructure is implemented in kernel + sim but not plumbed into LEAN.

### 52. 🔴 `LeanAdapter.commit` for buys overwrites `_holdings[ticker]` on top-up
- `algo._holdings[ticker] = HoldingState(entry_price=price, entry_date=today, …)`
  is unconditional. When the order is a top-up to an existing position,
  this *resets* `entry_date`, `entry_price`, `high_watermark`, and the
  thesis-A `entry_*_score` fields. Hold-day clocks restart, LT vs ST tax
  classification flips, trailing-stop trigger resets. **Catastrophic for
  performance attribution and tax accuracy in LEAN.**

### 53. 🔴 `RunnerAdapter.commit` resets entry state on every buy
- Same root bug as #52, in live:
  ```python
  self._entry_dates[ticker] = today_str  # unconditional
  self._sell_streaks.pop(ticker, None)
  self._last_sell_dates_str.pop(ticker, None)
  self._position_hwm[ticker] = price
  ```
  A top-up issued by `TopUpHeldTask` clears the existing sell streak
  and last-sell-date and resets HWM and entry_date. Only the wrap-up
  `max(prev, today)` ratchets HWM back if applicable.

### 54. 🔴 `SimAdapter._apply_sell` partial-sell sets `last_sell_dates[ticker] = today`
- Wash-sale guard on next bar reads this and blocks any TopUpHeldTask
  buy for `wash_sale_days` days. So Kelly-trim + same-bar/same-week
  Kelly-top-up cannot coexist — they ping-pong because the trim sets
  the wash-sale clock.

### 55. 🟠 `SimAdapter._apply_buy` top-up updates HWM with `today buy price`
- `high_watermark = max(prev_hwm, today's price)`. Buying at a *new*
  high properly updates HWM. Buying at a *lower* price leaves HWM
  alone — fine. But the prev-bar's HWM might have already been higher
  than today's buy price; that gets preserved but trailing-stop now
  arms tighter than it should after the top-up: cost basis
  weighted-averaged down, but HWM still based on the run-up.

### 56. 🟠 `SimAdapter.commit` exit loop allows duplicate ticker sells
- If `ctx.exits` contains the same ticker twice (stop_loss + trim
  collision via #21), `_apply_sell` is called twice. First call
  liquidates fully (`_pos_shares[ticker]` *not* updated until pop).
  Second call still sees `total_shares = first_call's amount`, sells
  again, credits cash twice. Because `full_exit_tickers` collected
  from both iterations, the final pop happens once — but `_apply_sell`
  has already fired twice. **Phantom cash bug.**

### 57. 🟡 `SimAdapter._build_feature_cache` skips SPY explicitly
- But the cache is later passed via `feature_cache_frame` in
  `TickerInferenceContext`. Held positions whose ticker is SPY (rare
  but possible if SPY in watchlist) get no cached frame and fall back
  to per-bar rebuild. Inconsistent perf vs other tickers.

### 58. 🟡 `RunnerAdapter` overwrites cached OHLCV in place during intraday overlay
- `df.at[last_day, "close"] = latest_close` mutates the parquet-loaded
  DataFrame. If `fetch_ohlcv` returns a cached DataFrame reference (it
  does), all subsequent calls in the same process see the modified
  frame. Sim or training that runs after the live path would see live
  intraday data leaked into yesterday's bar.

### 59. 🟡 `RunnerAdapter` `held_set` only includes watchlist symbols
- A position bought outside the watchlist (e.g. user manually bought
  NVDA before NVDA was added) is invisible to the runner forever.

### 60. 🟡 `SimAdapter.build_result.longest_no_candidate_streak` is read from `_monitor_state`
- But `_monitor_state` is mutated by `MonitorIdleStreakTask` each bar.
  After the loop ends, `_monitor_state["no_candidate_streak"]` is the
  *last bar's* streak, not the maximum. The "longest" naming is
  misleading; for streak monotonicity it works only because streak
  resets to 0 on each non-streak bar.

## 13. Kernel utilities — `kernel/{exits,sizing,scoring,data,…}.py`

### 65. 🔴 `kernel/data.py` `fetch_intraday_bars` references undefined `log`
- Line 410: `log.warning(...)` but no module-level `log = logging.getLogger(...)`.
  Calling `fetch_intraday_bars` during an Alpaca timeout raises
  `NameError: name 'log' is not defined` instead of the intended
  graceful degradation.

### 66. 🟡 `kernel/sizing.py` oversize fallback hardcodes 25 % (see #30)

### 67. 🟡 `kernel/sizing.py:compute_position_size` ignores BEAR override in
   the oversize fallback path
- Once the primary path can't fit a share, the 25 % retry uses
  `min(fallback_dollars, investable)`, but `investable` was overridden
  by `available_cash` in the BEAR branch. Edge case: BEAR + low cash →
  may still buy a high-priced single share at 25 % when the regime
  policy says <15 %.

### 68. 🟡 `kernel/portfolio.compute_trade_tax` returns 0 on losses
- Documented; but in tax-loss harvesting jurisdictions, a realised loss
  *creates* a tax credit (offset against future gains). Sim numbers
  understate the after-tax benefit of an exit at a loss.

### 69. 🟡 `kernel/scoring.calibrate` does not validate `method` enum
- `raise ValueError(f"Unknown calibration method: {self.method}")` only
  fires if method is set to a literal unknown string. A typo in JSON
  ("identy" instead of "identity") raises rather than gracefully
  falling back. Non-trivially destabilising in production retrain.

### 70. 🟡 `kernel/regime.compute_cusum` only checks the latest bar's
   z-score path against threshold
- The CUSUM accumulates s_pos/s_neg through `window`, then returns True
  if at any point during that walk the threshold is crossed. But the
  walk starts from 0 each call — so one giant outlier in the *first*
  bar of the window wipes the trail and the rest of the bars never
  accumulate. Standard CUSUM uses a running sum — this is a one-shot
  reset.

## 15. Training-panel / Panel-LTR — `training_panel/`

### 74. 🟠 `factors.py:cross_sectional_zscore` zero-substitution may bias
- `np.where((std > 0) & std.notna(), (val - mean) / std, 0.0)` —
  rows on dates where std is undefined get z=0. Combined with the
  later NaN restoration, these zero "neutral" values join the panel
  at rank 0.5 (median). For boundary dates with thin coverage, this
  artificially populates the median with non-informative noise.

### 75. 🟡 `labels._rolling_beta_purged` requires window+purge bars before β
- `min_periods=window` plus `shift(purge)` means the first `window+purge`
  rows have NaN β. Documented; just worth flagging — early sim bars
  produce NaN labels that get dropped.

### 76. 🟡 `pipeline.prepare_inference_panel_frames` uses `inference_only=True`
   to gate auto-fetch
- But the flag must be honoured by every loader (LoadFundamentalsTask,
  LoadEarningsSurpriseTask, LoadInsiderTradesTask, LoadHourlyBarsTask,
  LoadMinuteBarsTask). If any new loader is added without consulting
  this flag, an inference path could trigger a network fetch and stall.
  No central enforcement; relies on each loader honouring the contract.

### 77. 🟡 `pipeline.prepare_inference_panel_frames` does not call
   `LoadGlobalCalibrationTask` / NGBoost loaders
- They run inside the inference pipeline's `PanelScoringJob`, so this
  function only prepares feature/factor frames. Naming makes that
  ambiguous; the signature returns "feature, factor" but a reader
  might believe artifacts are also pre-loaded.

### 78. 🟡 `ngboost_head.predict_distribution` does not handle NaN in X
- Passes raw X to ngboost; ngboost happily returns NaN/inf predictions.
  Downstream μ−λσ clamps via `np.isfinite` checks but `panel_score =
  μ−λσ` may be NaN before that clamp lands.

### 79. 🟡 `global_calibrator.GlobalPanelCalibration.calibrate_probability`
   indexes empty knot arrays → IndexError
- `np.interp(..., left=self.prob_y[0], right=self.prob_y[-1])` crashes
  when `prob_y` is empty. Defensive wrap missing.

### 80. 🟡 `factors.compute_residual_momentum` uses **daily-return β** to
   neutralize **12-1 momentum** (yearly horizon)
- A one-day β doesn't match a one-year exposure. Standard practice in
  some quant literature, but worth documenting; otherwise readers
  expect mom-12-1-vs-mom-12-1 residualization.

### 81. 🟡 `factors.cross_sectional_zscore` post-winsorize variance != 1
- Clipping at ±3σ tightens distribution; the std on the winsorized
  output is < 1. Downstream consumers may be expecting unit-variance
  z-scores.

## 18. Cross-cutting & design issues

### 90. 🟠 Three places hold a "tuple-attr" bug for `ctx.exits` (#20, #21, #22)
- Search-and-replace for `getattr(e, "ticker"` across the repo finds
  all of them. They share root cause: `ctx.exits` is `list[(str, ExitSignal)]`,
  not `list[ExitSignal]` — the unpacking is missing.

### 91. 🟠 `Job.should_skip` deadcode pattern (see #1) means SelectionJob
   runs even with empty `ranked` list
- `SelectionJob.should_skip` returns `True` when `ranked` is empty, but
  it's never consulted. `RunSelectionTask` then calls
  `run_selection_loop([], …)` — no harm, returns `([], blocks={…:0})`.
  Cosmetic, but confirms the deadcode propagates.

### 92. 🟡 Tax rate defaults inconsistent across files
- `main.py`: 0.50/0.32 (clearly placeholders)
- `kernel.rotation.tax_drag`: 0.37/0.20
- `task_rotation.BuildPairsTask`: 0.37/0.20
- `SimAdapter`: 0.37/0.20
- `LeanAdapter` (commit): reads `algo._tax_short`/`_tax_long` set from main.py = 0.50/0.32
- Result: LEAN and sim/live tax computations can diverge by ~13 pp on a
  short-term gain when config keys are absent.

### 93. 🟡 Two parallel runners (`pipeline.run_parallel` and
   `pp_training.run_ticker_parallel`) duplicate logic
- Same exception handling, same timeout pattern, same worker resolver.
  Maintenance burden — fix #2 (cancel-not-actually-cancelling) needs to
  be applied in both places.

### 94. 🟡 `kernel/config.py` `STRATEGY_DIR` is module-scoped
- Two concurrent imports from different strategy dirs (e.g. test fixture
  loading 103 + 104) aliased the same module would produce stale
  `STRATEGY_DIR`. Each strategy has its own `kernel/` so this is in
  practice safe — but the design relies on Python's module cache being
  per-path which is fragile.

### 95. 🟡 No global exception handler in `InferencePipeline.run`
- If `SelectionJob` raises, the orchestrator propagates the exception
  out. Adapters' `commit()` is never called → state mid-bar lost (no
  exits committed, no trades logged). Live/sim recovers on next bar
  but the bar-in-progress state is gone.

### 96. 🟡 `record_pipeline_run` writes `commit_sha` via subprocess on EVERY
   bar. In a 700-bar sim that's 700 git invocations.
- Performance only.

### 97. 🟡 `monitor_state` JSON serialization through `live_state.json`
   doesn't validate counter types
- A corrupt state file (e.g. `"no_trade_streak": "ten"` from a manual
  edit) would propagate as string, then `+1` would silently coerce or
  raise depending on path. The `int(state.get("no_trade_streak", 0))`
  guard catches the obvious case but not embedded-in-dict copies.

### 98. 🟡 `score_artifact` returns `signal` from raw_score thresholds, but
   `rank_score` is calibrated probability — they may disagree
- E.g. raw_score = 0.05 (just above buy_threshold = 0.0 for some
  models) → signal=buy. rank_score = 0.20 (low calibrated probability).
  Selection sees a `buy` candidate but tier filters it out at the 0.10
  tier threshold. Asymmetric: candidate is *signalled* but not *selectable*.
  Documented behaviour; just tightly coupled to the calibration shape.

### 99. 🟡 `CandidateResult.detail` is f-string-built per candidate
- Cheap, but tens of thousands of small string allocations on a 600-bar
  × 40-ticker sim. Not a bug, just allocation pressure if scaled up.

### 100. 🟡 Several `getattr(c, "expected_return", 0.0) or 0.0` patterns
- `or 0.0` masks when `expected_return` is the literal float `0.0`. This
  is mostly harmless since 0.0 → 0.0 either way, but it conflates "no
  attribute / None" with "zero" — a recipe for silent mis-attribution
  if rotation logic later cares about the difference.

## Recommended first-fix priority list

1. **#51 + #52 + #53** — Top-up / partial-sell support is missing or
   broken in both LEAN and live. Today every top-up resets entry_date
   and entry_price; every partial sell in LEAN dumps the whole position.
   Quietest data-correctness destroyer in the tree. Fix: gate `_holdings[t] = HoldingState(...)`
   on "ticker not already held" in LeanAdapter & RunnerAdapter; add a
   "full liquidation vs partial sell" branch in LeanAdapter.commit
   honouring `sig.quantity`.

2. **#20 + #21 + #56** — TopUp/Trim guard the wrong type. Quick fix:
   ```python
   already_selling = {t for t, _ in (ctx.exits or [])}
   ```
   Then audit `_apply_sell` to reject duplicate-ticker exits.

3. **#22** — `_notify_decision` reports `EXIT ? (?)`. Same fix pattern
   as #20 — unpack the tuple.

4. **#65** — `kernel/data.fetch_intraday_bars` will NameError on
   timeout. Add module-level logger.

5. **#9** — Hurst polyfit lag/value misalignment. Track the lag per
   `rs_chunk` instead of regenerating from `range`.

6. **#26 + #33** — Rotation EmitTask ignores Kelly + cooldown +
   per-session-cap that selection respects. Either funnel both surfaces
   through a shared `size_for_buy(c, ctx)` helper or duplicate the
   missing branches into EmitRotationsTask.

7. **#54** — Partial sell triggers wash-sale clock inappropriately.
   Don't set `last_sell_dates[ticker]` on partial trims; let the next
   full liquidation own that field.

8. **#1** — Drop `should_skip` from `Job` / `TickerJob` (or honour it
   inside `Job.run`). Either way, dead-code masks intent.

9. **#15** — Order BEAR / Confidence-veto / BullVol checks **after**
   velocity & EMA gates, or have them not return False so all gates
   fire and update counters consistently.

10. **#46 + #87 + #92** — Reconcile benchmark + tax-rate defaults across
    files. Pick one default per concept, document it.
